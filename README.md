# Property Listings API

A public, read-mostly REST API for a Nigerian residential property market: estate agencies, the
agents who work for them, the properties those agents list for sale or rent, and viewing requests
made against those listings. Anyone can call it; no key or account is needed to read.

- **Live API:** `https://API_HOST/api/v1` (replace `API_HOST` below with the deployed host)
- **Consumer:** [`consumer/`](consumer/), a single page that calls the live API
- **Seed script:** [`api/scripts/seed.ts`](api/scripts/seed.ts)

Try it:

```bash
curl "https://API_HOST/api/v1/listings?city=Lagos&listingType=rent&sort=price&order=asc&limit=3"
```

## Resource design

Four resources. Each one references the one above it:

```
agencies 1 ──< agents 1 ──< listings 1 ──< viewings
```

- An **agency** employs many agents.
- An **agent** belongs to exactly one agency and manages many listings.
- A **listing** is managed by exactly one agent and receives many viewing requests.
- A **viewing** is a request by a member of the public to see one listing at one time.

Every identifier is a UUID (v4), generated by the database on insert, never a sequential integer.

### `agencies` (200 seeded)

| Field         | Type     | Required | Notes                              |
| ------------- | -------- | -------- | ---------------------------------- |
| `id`          | uuid     | yes      | generated                          |
| `name`        | string   | yes      | sortable, searchable with `q`      |
| `city`        | string   | yes      | filterable                         |
| `state`       | string   | yes      | filterable (Nigerian state)        |
| `phone`       | string   | yes      |                                    |
| `email`       | string   | yes      |                                    |
| `foundedYear` | integer  | yes      | 1950 to 2100, sortable             |
| `createdAt`   | ISO 8601 | yes      | sortable                           |
| `updatedAt`   | ISO 8601 | yes      |                                    |

### `agents` (400 seeded)

| Field             | Type     | Required | Notes                                |

### `listings` (800 seeded)

| Field          | Type     | Required | Notes                                                             |
| -------------- | -------- | -------- | ----------------------------------------------------------------- |

| Field            | Type     | Required        | Notes                                                        |
| ---------------- | -------- | --------------- | ------------------------------------------------------------ |
| `id`             | uuid     | yes             | generated                                                    |
| `listingId`      | uuid     | yes (on create) | references `listings.id`; the listing must be `active`       |
| `requesterName`  | string   | yes (on create) | 1 to 120 characters                                          |
| `requesterEmail` | string   | yes (on create) | valid email                                                  |
| `scheduledFor`   | ISO 8601 | yes (on create) | must include a timezone offset and be in the future          |
| `status`         | enum     | yes             | `requested` (default), `confirmed`, `cancelled`, `completed` |

| `updatedAt`      | ISO 8601 | yes             |                                                              |

## Conventions every endpoint follows

**Base URL.** Every path starts with `/api/v1`.

**Success envelope.** A list returns `data` (an array) and `meta`. A single item returns `data` (an object).

```json
{
  "data": [ ... ],
  "meta": { "total": 22, "limit": 20, "hasMore": true, "nextCursor": "eyJzIjoi..." }
}
```

| `meta` field | Meaning                                                                      |
| ------------ | ---------------------------------------------------------------------------- |
| `total`      | how many records match the filters, across all pages                         |
| `limit`      | the page size actually used, after clamping                                  |
| `hasMore`    | whether another page exists after this one                                   |
| `nextCursor` | pass as `?cursor=` to get the next page; `null` on the last page             |

**Error envelope.** Every error, with every status code, has this shape. `details` appears when
specific fields or parameters are at fault.

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The request body failed validation",
    "details": [{ "field": "requesterEmail", "message": "is required" }]
  }
}
```

**Pagination, filtering, sorting (every list endpoint).**

| Parameter | Type    | Default           | Rules                                                                    |
| --------- | ------- | ----------------- | ------------------------------------------------------------------------ |
| `limit`   | integer | `20`              | at least 1; values above `100` are clamped to `100`                      |
| `cursor`  | string  | none (first page) | only a `meta.nextCursor` value from the same sort, order, and filters    |
| `sort`    | enum    | per endpoint      | one of that endpoint's sort fields; anything else is `400`               |
| `order`   | enum    | per endpoint      | `asc` or `desc`                                                          |
| filters   | varies  | none              | listed per endpoint; an unknown parameter is `400`, not silently ignored |

`offset` is not accepted: this API paginates by cursor (see [Design decisions](#design-decisions)).
Sending `?offset=` returns a `400` that says so.

**Status codes.**

| Status | Code(s)                                                   | When                                                                  |
| ------ | --------------------------------------------------------- | --------------------------------------------------------------------- |
| 200    |                                                           | successful read or update                                             |
| 201    |                                                           | viewing created; `Location` header points at it                       |
| 204    |                                                           | viewing deleted                                                       |
| 400    | `INVALID_QUERY`, `INVALID_CURSOR`, `INVALID_JSON`         | bad query parameter, bad or mismatched cursor, unparseable JSON body  |
| 404    | `NOT_FOUND`                                               | no such record (a malformed id is also a 404), or no such endpoint    |
| 409    | `SLOT_TAKEN`, `LISTING_UNAVAILABLE`, `VIEWING_CLOSED`     | request conflicts with current state                                  |
| 413    | `PAYLOAD_TOO_LARGE`                                       | body over 10 KB                                                       |
| 422    | `VALIDATION_FAILED`                                       | well-formed body with invalid or missing fields; each field is named  |
| 429    | `RATE_LIMITED`                                            | more than 100 requests in 60 s from one IP; `Retry-After` is set      |
| 500    | `INTERNAL_ERROR`                                          | a bug; details are logged server-side, not returned                   |

**Rate limit.** 100 requests per 60-second window per client IP. Every response carries
`X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (seconds). A `429` also carries
`Retry-After` (seconds).

**Money.** Prices are integers in minor units (`priceMinor`, in kobo) with a `currency` beside them.
`priceMinor: 165000000` with `currency: "NGN"` means ₦1,650,000. Price filters also use kobo.

Viewings hold a member of the public's name and email, so there is deliberately **no endpoint
that lists viewings**. The `id` returned when a viewing is created is the only way to read or
change it (see [Design decisions](#design-decisions)).

## Design decisions

### Why these resources

Property is a market where the relationships are the product: a buyer searches **listings**, trusts
the **agent** by experience, and the **agency** for its standing. Three read-only resources in a chain
(`agencies → agents → listings`) exercise nested endpoints and foreign keys. The fourth,
**viewings**, is the one thing a member of the public creates, so it carries the `POST`, `PATCH`, and
`DELETE` endpoints and the write-side rules: validation, a state that can close, and a real
conflict (two people booking the same listing at the same time).

Viewings have no list endpoint. Each viewing holds someone's name and email, and this API has no
authentication, so a public list would publish every requester's contact details. The UUID
returned at creation works like the brief's `GET /orders/:id`: whoever holds it can see and manage
that one viewing.

### Why generated identifiers

With sequential integers, `GET /listings/1`, `/2`, `/3` walks the whole dataset, and the highest id
tells a competitor how many listings, agents, or viewings exist. That matters most for viewings,
where the id is the only thing protecting a requester's personal data: a sequential viewing id
would let anyone read every viewing by counting. UUID v4 ids have 122 random bits, so they can't be
guessed or enumerated. They are generated by Postgres (`gen_random_uuid()`) so every insert gets
one, whichever code path does it. A malformed id is rejected before it reaches the database and
returns `404`, never a `500` from a failed uuid cast.

### Why cursor pagination, not offset

Offset pagination (`LIMIT 20 OFFSET 400`) makes Postgres read and throw away 400 rows to return 20,
so deep pages get slower. It is also unstable: if a new listing is inserted while a client is
paging, every later page shifts by one and the client sees a duplicate or misses a row.

A cursor records where the last page ended: the last row's sort value and its id. The next page
asks for rows strictly after that point:

```sql
where (price_minor, id) > ($1::bigint, $2::uuid)
order by price_minor asc, id asc
limit 21
```

With the `(price_minor, id)` index this is an index seek at any depth, and rows inserted elsewhere
cannot shift it. The `id` tiebreaker is not optional. All 1,900 seeded rows share one `createdAt`,
because they were inserted in one transaction. Sorting by `createdAt` alone would give no stable
order, and a cursor holding only the timestamp would skip or repeat rows. With `id` added, the
order is total.

The cursor also records the sort, order, and a hash of the filters it was issued under. Reusing a
cursor with different parameters returns `400 INVALID_CURSOR` rather than a silently wrong page.
Sort values that are timestamps go into the cursor as Postgres's own text form, not a JavaScript
`Date`, which would drop the microseconds and make the comparison wrong.

**When offset is the better choice:** when users need to jump to an arbitrary page ("go to page 7
of 30"), for example a numbered admin table. A cursor can only move forward from a known point. For
small, rarely changing collections, offset is also simpler and its costs are negligible. This API
serves feeds and filtered searches that clients page through, so cursor fits. `total` is still
returned so a client can show "22 listings".

**Asking past the last page.** There are no page numbers to ask for: a client can only follow
`nextCursor`, and the last page returns `nextCursor: null` and `hasMore: false`. A hand-made or tampered cursor is rejected with `400 INVALID_CURSOR`. A valid
cursor whose rows have since been deleted still works: it returns whatever rows come after that
point, possibly an empty `data` array with `hasMore: false`.

### Why this envelope

```json
{ "data": ..., "meta": { "total", "limit", "hasMore", "nextCursor" } }
{ "error": { "code", "message", "details"? } }
```

- **`data` is always the payload key**, for one item or many, so a client reads `response.data`
  everywhere and never has to guess the shape per endpoint.
- **`meta` sits outside the data** so pagination can grow (for example a `prevCursor`) without touching the records.
- **`meta.limit` echoes the limit actually applied**, so a client that asked for 5000 can see it got 100.
- **Errors have a separate top-level `error` key and an honest status code**, so a client can
  branch on `response.error` or on the status and never mistakes a `200` for success when it
  wasn't. `code` is stable and machine-readable; `message` is for humans and may change.
  `details` names each offending field or parameter.

### Where the limits live, and why

The page size defaults, the maximum page size, and the rate-limit numbers are all in
[`api/src/config.ts`](api/src/config.ts), not in handlers. Every list endpoint and the rate
limiter read them from there, so a change is a one-line diff reviewed in one place, and no handler
can drift to its own limit.

The rate limiter is a fixed-window counter held in memory, keyed on client IP. `trust proxy` is set
to one hop, because on Render `req.socket` is Render's proxy, not the client; without it every
request would share one bucket. In-memory is correct for a single instance. Scaling to several
instances would need the counter in a shared store (Redis or Postgres), or each instance would
allow its own 100.

### Adding a field without breaking clients

Adding a field is backwards-compatible in this design and needs no new version. For example, to
add `furnished` to listings:

1. Add a migration `002_listings_furnished.sql`: `alter table listings add column furnished boolean not null default false`. The default fills existing rows, so no `null` appears.
2. Add `furnished` to the `select` list in `listingsSpec`. Existing clients ignore keys they don't know.
3. If it should be filterable, add it as an optional query parameter. Omitting it keeps the current behaviour.
4. Document it here.

What would need `/api/v2` is a breaking change: renaming or removing a field, changing a type (for
example `priceMinor` becoming a string), or changing what a field means. That would ship under
`/api/v2` while `/api/v1` keeps serving existing clients.

### Validation in one place

Every query string and body is parsed by a strict [Zod](https://zod.dev) schema declared next to its
route. Query problems return `400 INVALID_QUERY` and body problems `422 VALIDATION_FAILED`, both
naming each field. Unknown parameters are rejected rather than ignored: a typo like `?minprice=`
would otherwise silently return unfiltered results that look correct. The rules the database must
never break (unique agent email, positive integer price, valid status, no double-booked slot) are
also constraints in the schema, so they hold even for writes that skip the API.

## Running it locally

Requirements: Node.js 20 or newer, and a Postgres 13+ database (a free Supabase project works).

1. Clone and install the API:
   ```bash
   git clone <this repo>
   cd engineering-task-1-consumable-api/api
   npm install
   ```
2. Create `api/.env` from the example and set `DATABASE_URL`:
   ```bash
   cp .env.example .env
   ```
   For Supabase: **Project Settings → Database → Connection string → Session pooler**. Use the
   pooler string (IPv4); the direct connection is IPv6-only and fails from many networks and from Render.
3. Create the tables:
   ```bash
   npm run migrate
   ```
4. Load the data (200 agencies, 400 agents, 800 listings, 500 viewings). Safe to run more than once:
   ```bash
   npm run seed
   ```
5. Start the API on http://localhost:3000:
   ```bash
   npm run dev
   ```
   Check it: `curl "http://localhost:3000/api/v1/listings?limit=2"`
6. Run the consumer (in a second terminal):
   ```bash
   cd ../consumer
   npm install
   cp .env.example .env    # set VITE_API_BASE_URL to the deployed API, e.g. https://API_HOST/api/v1
   npm run dev
   ```
   Open the URL Vite prints (http://localhost:5173).

### Seed repeatability

Faker is seeded with a fixed number and reference date, so the script generates the same records
every time, including the same UUIDs, and every insert is `on conflict (id) do nothing`. A second
run inserts nothing:

```
$ npm run seed
inserted this run: { agencies: 200, agents: 400, listings: 800, viewings: 500 }
rows in database:  { agencies: 200, agents: 400, listings: 800, viewings: 500 }
$ npm run seed
inserted this run: { agencies: 0, agents: 0, listings: 0, viewings: 0 }
rows in database:  { agencies: 200, agents: 400, listings: 800, viewings: 500 }
```

Viewings created later through the API have database-generated UUIDs, so they never collide with seeded ones.

## Deploying it

The API runs as a Render web service. The database is a managed Postgres on Supabase.

1. Create a Supabase project and copy its **Session pooler** connection string.
2. From your machine, with that string as `DATABASE_URL` in `api/.env`, run `npm run migrate` then `npm run seed`.
3. In Render, choose **New → Blueprint** and point it at this repository. [`render.yaml`](render.yaml)
   defines the service (`rootDir: api`, build `npm ci && npm run build`, start `npm start`).
4. When prompted, enter `DATABASE_URL`. It is set in the Render dashboard only, never committed.
5. When the deploy is live, check it from a network that is not yours (a phone on mobile data):
   `curl "https://API_HOST/api/v1/listings?limit=1"`.

The free Render instance sleeps after 15 minutes idle. The first request after that takes around 30
to 60 seconds while it wakes, and later requests are fast.
